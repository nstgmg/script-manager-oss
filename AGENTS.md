# Script Manager — Agent Instructions

Build reusable deterministic scripts; Script Manager operates them. Natural language describes the purpose, and conventional code implements repeatable work. A Job defines what to execute; its Schedules define when. Multiple Schedules may belong to one Job.

## Start and discover

- Read [README](README.md), [INSTALL](INSTALL.md), [CLI](docs/cli.md), [authoring](docs/script-authoring.md), and relevant source before using an interface. Inspect `python -m runner --help` and subcommand help; do not invent Package/lifecycle/service commands.
- Prefer maintained Python 3.13 for a fresh venv; keep the code minimum at 3.9 unless separately authorized. An external Windows/Python 3.14.3 basic-install success is a reported validation, not proof for all configurations. Follow INSTALL for runtime preparation. Windows uses `.venv\Scripts\python.exe`; POSIX uses `.venv/bin/python`. `--root ROOT` precedes the command and selects writable data, not module search paths.
- Empty installations need no credentials. The network-free [hello-output](examples/hello-output/README.md) example explains registration and first verification. Never overwrite an existing ID.
- CLI is the default. Start Dashboard only on an explicit service request, after checking existing services and session root. Reuse a verified same-root service. Do not restart/terminate existing services or Jobs to fix observation errors. The optional [Skill](.agents/skills/sm-dashboard/SKILL.md) documents the workflow.

## Route natural-language requests

Users should not need to locate technical manuals or memorize commands. Read the relevant documents yourself, explain the next step in plain language, and use the supported interfaces for authorized work.

| User intent | Read or inspect first | Response and action boundary |
| --- | --- | --- |
| “What can this do?” | [Capabilities](docs/capabilities.md) | Explain purpose-based examples, built-in management versus scripts to author, and platform limits. Do not create or run work from a capability question. |
| “How do I use it?” or a desired workflow | [User guide](USER_GUIDE.md), then the linked technical contract | Give a copyable request and propose inputs/results. For new automation, inspect existing Jobs first and follow authoring guidance. |
| Repository URL + installation request | [INSTALL](INSTALL.md), then the installation workflow below | Use an isolated writable location and verify the offline example only within the documented installation scope. |
| “Check for updates” / “업데이트 확인해 줘” | [UPDATE](UPDATE.md), local VERSION/HEAD/worktree, official stable Releases | Inspect and explain only; do not switch code, install dependencies, migrate data or control services. |
| “Update Script Manager” / “업데이트해 줘” | [UPDATE](UPDATE.md), Release Notes/migrations, data and execution state | Explain the plan, then apply only the authorized safe scope. Preserve local changes; defer conflicts, incompatible changes and running work. No stable Release means no stable update; never substitute latest main. |
| Current Jobs, runs, schedules or saved results | [CLI](docs/cli.md), [result queries](docs/result-queries.md), actual local runtime | Use `list`/`get`, `runs`/`logs`, `schedule-status`, or `result-jobs` → `results` as appropriate. Documentation and the public example are not evidence of the user's current Jobs or data. |
| Dashboard management | [User guide](USER_GUIDE.md#dashboard에서-관리하기), [INSTALL service procedure](INSTALL.md#4-선택적-dashboard-시작과-종료) | Explain the UI; inspect and reuse a verified service. Start only on an explicit service request. Read the optional Skill for that request if the host does not discover it. |

If the purpose is unclear, offer a few easy choices such as “create a recurring task”, “see saved results”, or “manage in a browser”; continue independent read-only discovery. Ask only for consequential ambiguity or missing required inputs without safe defaults. “I want daily announcements” leaves source and time unresolved: prepare the script/disabled schedule proposal, then obtain the required execution and activation authorization. Do not infer real collection, active scheduling, service startup or SSH permission from a general goal or a question. An explicit execution/service request is authorization within its scope; do not ask again for already authorized actions. Keep all existing approval, secrets, network and process-preservation rules below.

## Installation request workflow (agent-neutral)

- A repository URL plus an installation request authorizes a new isolated checkout/venv, declared dependencies, lazy initialization with list, and one offline synthetic hello-output registration/run/result check per [INSTALL](INSTALL.md). It does not authorize real Jobs, external collection, native schedules, SSH deployment or Dashboard startup.
- Read INSTALL even when the host does not auto-discover this file. No agent-specific Skill, copied development venv, API key or shell activation is required. Choose a new user-owned directory; preserve existing installations. If required Git authentication, tools or approved network access are missing, report the missing prerequisite; never inspect credentials or bypass restrictions.
- Codex and Claude Code must install on the user's target OS/filesystem using its available terminal. Record OS, shell/version, Python executable/version and absolute code/data/project roots before changing directories. A WSL/Linux container or remote macOS test does not establish native Windows installation. If the target terminal is unavailable, report that boundary and provide prepared commands; do not claim completion.
- Discover existing installations before cloning: inspect the specified/current/project destination including hidden entries, repository identity, VERSION/HEAD/worktree and local venv. Never nest a duplicate clone, overwrite a nonempty folder, pull/reset existing code or rebuild an existing venv as routine setup. Existing installation means inspect `list/get/runs/results` first, no automatic pip upgrade or example rerun. A failed clone stays preserved; choose a new location only after classification.
- Run `py -3 scripts/bootstrap.py` on Windows (or the selected Python on POSIX) for read-only runtime status. Use `--prepare` only for a confirmed new/partial environment without operating data; it preserves working environments, stops on the first failed stage and never initializes Jobs/services. Its default-root `data_paths` cannot discover a separately configured data root. Incomplete/broken/linked venvs and operating data require diagnosis, not automatic deletion/recreation. Follow INSTALL's recovery table and preserve Jobs, Schedules/OS registrations, Output, State, Workspace, secrets and deployment history.
- PowerShell 5.1: quote executable paths and use `&`; inspect `$LASTEXITCODE` immediately after each native command. Do not use PS 7-only `&&`/`||`, rely only on `$ErrorActionPreference` for native failure, activate the venv, change execution policies or elevate. Bootstrap uses argv subprocesses and disables pip progress/color without global configuration. A PSReadLine hypothesis needs stack evidence; do not label the reported array exception fixed without actual reproduction. CMD/profile-free diagnosis reuses the same checkout/venv and starts with status, never another clone/submission.
- For Codex, finish installation with project-local Dashboard Skill registration per [INSTALL](INSTALL.md#codex-프로젝트의-dashboard-skill-등록). Capture the agent's actual project root before changing into the checkout; it is not necessarily the checkout's Git root or the shell's later cwd. If the roots match, keep the repository Skill. If the checkout is nested, run `python scripts/register_dashboard_skill.py --project-root ABSOLUTE_PROJECT_ROOT` from the checkout (using its venv), then repeat with `--check`. POSIX uses a symlink; Windows uses a copy plus source locator. Keep the original. Never use a global Skill directory, replace existing files, infer an ambiguous parent, or write outside approved paths. Report conflicts/missing access with the proposed exact source/destination; installation permission does not bypass sandbox approval. Skill registration does not authorize service startup.
- Verify discovery separately from registration: check the current host's Skill list/picker when available, without manually registering or reopening the folder. An App Server client can use `skills/list` with `cwds` and `forceReload: true` on its current server; a separate server cannot refresh the current app's cache. For a fresh-session test, use the same project root and check the automatically discovered Skill path and explicit-only policy before any invocation. A readable SKILL.md or successful `--check` is only filesystem evidence. Distinguish fresh-session discovery from live-session reflection. If the host provides no listing/refresh capability or a fresh session cannot be tested, report that limit; for an explicit Dashboard request, read the original Skill directly. Do not claim automatic discovery or require a folder reopen as the normal installation step.
- Inspect help and implementation, verify the empty root, copy reviewed example source only after successful create, submit once and retain the Run ID. Verify terminal state/exit code, both logs, the actual result.json (`complete=true`, alpha/beta two records) and saved-result query total 2 / Alpha total 1. Preserve an existing example after partial setup and inspect get/runs before deciding recovery; never blindly copy over it or submit another Run. If this installation request created the example and no Run exists, resume only its verified incomplete steps under the existing authorization. Report actual paths, platform and warnings. Observation failures resume the same Run; do not resubmit. Runtime dependencies alone mean environment prepared, not installation verified. Distinguish actual host tests, OS adapter simulations, external user reports and pending native verification.
- Dashboard requires a separate explicit service request; inspect existing services/root and use INSTALL start/stop instructions. Close only a temporary test server whose lifecycle was explicitly authorized. Do not infer service permission from an install request or HTML rendering.

## Product version and update workflow

- Root [VERSION](VERSION) is the product version, corresponding to official Release Tag `vX.Y.Z`; it is separate from Job/config/parameter contract versions. `0.1.0` is the planned first distribution version, not a published Release yet. VERSION or a Tag alone does not prove an official stable installation.
- Installation follows INSTALL; existing-install updates follow [UPDATE](UPDATE.md). Check local VERSION, HEAD, worktree and remote identity, compare official non-draft/non-prerelease Releases, and review all intervening Release Notes and migrations. A missing VERSION means unrecorded version: identify by HEAD; do not assign a version or reinstall over it. Distinguish network/access failure from no Releases.
- Before applying, preserve user Jobs, Schedules and OS registrations, Output, State, Workspace, settings, secrets, environments, Packages and history. Check queued/running Jobs, Dashboard/session root and active schedules. Never overwrite local changes or cancel/restart work to make updating possible. Explain conflicts and obtain only the additional decisions/authorization actually needed.
- An explicit update request authorizes the safe product-code/declared-dependency scope after plan disclosure; a check request authorizes inspection/reporting only. Do not infer data migration, active Schedule changes, service control or real Job execution. Do not auto-update, blindly pull main, reset/clean, force push or rewrite history.
- Verify version/HEAD, CLI, existing Job list and affected essential features with minimal checks. Do not repeat new-install example registration in live data or a full regression/security audit by default. Check existing project-local `sm-dashboard` registration with the existing script per INSTALL/UPDATE; preserve external files and explicit-only policy, never globally install. Report registration separately from host discovery.
- Report the actual version/HEAD, validation and remaining work. On failure use the reviewed code/environment recovery procedure in UPDATE; never delete or roll back operating data as part of code recovery.

## Author Jobs

- Keep executable code, dependency declarations, README and `job.yaml` in `jobs/{id}/`. Real Jobs are Git-ignored; public examples belong in `examples/` and must use synthetic data.
- Use supported `create`/etag `update` for YAML and edit scripts directly. Preserve existing contracts and worktree changes. Job metadata uses only validated fields; no separate management JSON.
- Propose safe defaults: manual schedules `[]`, 300-second timeout, argv array, standard Output/State paths, bounded input and retries, nonzero exit for required failures. Ask only for consequential ambiguity or required missing inputs.
- Follow [script-authoring](docs/script-authoring.md) for atomic writes, idempotence, logs, failure recovery and verification. Record decisions in existing metadata and the Job README.
- Discover execution inputs only from `get JOB_ID` → `config.parameters`, not script source. Pass declared public types through `--parameters`; never put secrets there. Report the accepted Run's parameters/contract version.

## Execute and observe

- An explicit existing-Job execution request authorizes one submission. Use `run JOB_ID --wait` in a suitable execution environment. Save the Run ID; queued/202 is acceptance, not success.
- Success requires `state: succeeded`, exit code 0, stdout/stderr inspection and expected saved Output. Resume observation of the same Run after a timeout or transport error; do not blindly submit again.
- Restricted agent networking is inherited by detached workers. For network Jobs, use an approved existing resident Dashboard through `run-dashboard` only after session root verification. If unavailable, report access limits; do not start a service or switch to browser automation as a workaround.
- `run-dashboard --run RUN_ID` observes an existing Run. Keep CSRF only in memory, preserve Host/Origin checks and never print session responses/tokens.
- Saved-data questions use `result-jobs` then `results`, with supported filters and pagination. Do not recollect, visit source URLs or search the web without an explicit refresh request. Report collection time, source/Run/path, stale/partial/unknown warnings; do not silently use older data or merge rows.

## Data and secrets

- Use `SCRIPT_MANAGER_OUTPUT_DIR`, `SCRIPT_MANAGER_STATE_DIR`, `SCRIPT_MANAGER_WORKSPACE_DIR` and `SCRIPT_MANAGER_JOB_DATA_ROOT`. Output, durable State and shared Workspace have distinct ownership. Do not edit another Job's results without authorization.
- Read root `.env.example` for names; reuse names where applicable. Real values are registered directly by the user in root `.env`; agents must not read, copy, print or persist them. Declare required names in `required_env`. Do not combine it with legacy `env_file` or create new Job-specific env files.
- `.env.example` contains empty assignments only. Secrets never belong in command/YAML env/parameters, source, logs, fixture, Package or report. stdout/stderr are not automatically redacted. POSIX secret permissions must be 600; Windows needs suitable ACLs.
- Keep credentials-dependent schedules disabled until preflight and an authorized real success verify setup. Never copy runtime, real targets, generated reports, Package/history or user Jobs into the source distribution.

## Approval and boundaries

- Never delete or overwrite an existing Job/Schedule without explicit authorization. Obtain approval for active Schedule changes, destructive cleanup, SSH deployment/rollback and other consequential external writes. Supported Schedule management applies YAML and OS together; inspect observed OS status.
- Package download is an immutable export, not install/run. Use an existing Package ID and matching offline `plan_hash` for authorized SSH deployment. Never replace Packages or erase deployment history. Preview lifecycle candidates; preserve protected releases. Output cleanup moves to trash and does not reclaim disk space.
- No automatic OS scheduling, SSH, deployment, native integration tests or services during routine setup. Tests use isolated roots; native Schedule tests require explicit opt-in and approval. Preserve unrelated processes and data.
- Dashboard is loopback-only, single-user and not a sandbox. Keep security checks intact. Linux local Schedule application is unsupported. Windows basic installation/example/results have an external success report; native scheduling, new recovery commands and Windows Dashboard remain unverified. Real remote Linux is unverified. Remote `required_env` and standard local runtime paths are not supported; read [packages](docs/packages.md).
- Do not claim unverified platforms or work as successful. Record actual tests/skips and unresolved risks. Installed-product updates follow [UPDATE](UPDATE.md); maintainer source transfers follow [CONTRIBUTING](CONTRIBUTING.md).
