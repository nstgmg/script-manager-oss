# 초기화·완전 삭제·남은 예약 복구

Script Manager 폴더를 먼저 지우면 OS에 예약이 남을 수 있습니다. **먼저 예약을 해제하고 확인한 뒤 데이터를 삭제**하세요. 초기화와 제거 준비는 아래 명령으로 범위를 미리 보여 주며, 확인값 없이 삭제하지 않습니다. 자동 삭제나 별도 감시 서비스는 없습니다.

## 무엇을 선택하나요?

| 목적 | 방법 | 작업이 끝난 뒤 |
| --- | --- | --- |
| 모든 작업과 데이터를 비우고 계속 사용 | Dashboard의 **관리 · 초기화**, 또는 `reset` | 프로그램과 가상환경을 그대로 사용 |
| Script Manager를 더 이상 사용하지 않음 | CLI의 `uninstall` 후 정상 종료, 폴더 직접 삭제 | 프로그램 폴더까지 사용자가 제거 |
| 폴더를 이미 삭제했거나 예약 상태가 이상함 | 같은 OS 계정에서 재설치 후 `schedule-doctor` | 소유가 확인된 고아 예약만 개별 승인하여 제거 |

초기화·제거 준비는 되돌릴 수 없는 영구 삭제입니다. 필요한 Job 소스·결과·자격증명은 사용자 관리 위치에 먼저 백업하세요. 에이전트에게 `.env` 비밀값을 읽거나 출력하게 하지 마세요. 스크립트의 외부 부작용, 클라우드 계정, 원격 배포 서버를 되돌리거나 제거하는 기능은 아닙니다.

## 삭제 대상과 보존 대상

대상은 명령의 `--root`로 선택한 **데이터 폴더 하나**입니다. 생략하면 현재 폴더입니다. 실제 목록은 미리보기의 `root`, `delete`, `schedules`로 확인합니다.

| 영구 삭제 | 설명 |
| --- | --- |
| `jobs/`의 사용자 항목 | Job 정의, 사용자 스크립트·의존성 선언·README·Job 내부 파일. `.gitkeep` 보존 |
| `runtime/`의 사용자 데이터 | 실행 기록·캡처 소스·로그, Output·State·Output 휴지통, Job 휴지통·YAML 백업, 보존 정책, 예약 적용 기록, 보고서 메타데이터, 배포 상태 |
| `workspace/`, `reports/`, `exports/` | 공유 작업 파일, 기본 보고서, 내보내기 |
| `deployments/packages/`, `deployments/history/` | ZIP·Package 메타데이터와 로컬 배포 이력. 이 명시적 전체 초기화는 개별 Package 보존 설정보다 우선 |
| `deployments/targets.yaml`, `deployments/targets.local.yaml` | 사용자 배포 대상 설정 |
| 루트 `.env` | 자격증명 저장 파일. 미리보기는 이름·파일 정보만 확인하며 내용은 읽지 않음 |
| 현재 설치본의 확인된 OS 예약 | 데이터 삭제 전에 해제·검증 |

보존하는 것은 다음과 같습니다.

- 프로그램 소스(`runner/`, `dashboard/`, `deployments/`의 Python 코드 등), 문서·예제, `.git`, `.venv`, `.env.example`.
- `runtime/installation.json`의 설치 ID, `runtime/locks/`의 잠금 파일, `runtime/doctor-notice.json`의 첫 실행 진단 표시 기록. 잠금 파일의 기존 inode를 유지해 동시 작업을 안전하게 차단합니다.
- 위 표에 없는 사용자 지정 폴더·루트 파일, 외부 위치의 보고서·백업, 다른 설치본, OS 계정·SSH 키·OS/Python 설치.
- 원격 서버의 배포 디렉터리·실행 기록·systemd 예약. 로컬 `reset`/`uninstall`은 SSH에 접속하지 않습니다.

사용자 지정 보고서가 위 삭제 대상 디렉터리 안에 있다면 함께 삭제됩니다. 그 밖의 경로는 같은 프로젝트 폴더 내부여도 자동 삭제하지 않습니다. `--root`로 코드와 데이터를 분리했다면 두 폴더를 각각 확인하세요. 프로그램 폴더 전체를 나중에 직접 삭제하면 그 안의 보존 항목도 없어집니다.

심볼릭 링크·Windows junction/reparse point·특수 파일·별도 마운트(Linux의 같은 장치 bind mount 포함)·중첩 설치본이나 Git 프로젝트가 삭제 대상에 발견되면 보수적으로 중단합니다. 코드 없는 별도 데이터 루트의 설치 ID도 중첩 설치본으로 보호합니다. 외부 경로를 따라가 지우지 않습니다.

## CLI로 사용자 데이터 초기화

터미널에서 `runner/`가 있는 코드 폴더로 이동합니다. macOS/Linux 예시입니다. Windows PowerShell에서는 `.venv/bin/python`을 `.\.venv\Scripts\python.exe`로 바꿉니다.

```sh
.venv/bin/python -m runner reset --help
.venv/bin/python -m runner reset
```

첫 명령은 도움말, 두 번째 명령은 **미리보기**입니다. 데이터 폴더가 별도 위치라면 항상 같은 `--root`를 명령 앞에 지정하세요.

```sh
.venv/bin/python -m runner --root "/absolute/data-folder" reset
```

결과에서 다음을 확인하세요.

1. `root`가 비우려는 데이터 폴더인지 확인합니다.
2. `active_runs`, `schedules`, `delete`에 표시된 영향 범위를 검토합니다. `bytes`는 파일 크기 합계이며 실제 확보 공간과 다를 수 있습니다.
3. `blockers`가 있으면 중단 이유를 해결합니다. 대기·실행 중·상태 불명확인 작업이 있으면 강제 종료하지 않습니다. 과거 실행 기록만 남았다면 `runs JOB_ID`로 상태를 다시 확인할 수 있습니다.
4. 삭제에 동의하면 반환된 `plan_hash`를 복사해 아래 `확인값`을 바꿉니다. 문서의 단어 자체를 입력하지 마세요.

```sh
.venv/bin/python -m runner reset --confirm 확인값
```

`--root`를 사용했다면 승인 명령에도 똑같이 사용합니다. 미리보기 이후 데이터·예약이 바뀌면 확인값이 거부됩니다. **새 미리보기를 검토한 뒤** 다시 승인하세요. 실행 중 승인 대기를 위한 프로세스나 상주 서비스는 만들지 않습니다.

승인 후 순서는 실행·소유권 재확인 → 현재 설치본 OS 예약 해제 → 실제 해제 재조회 → 승인한 데이터 목록 재대조 → 승인된 항목만 개별 삭제 → 남은 데이터 검사입니다. `success: true`, `phase: complete`일 때 완료입니다. 이후 `list`에서 빈 Job 목록을 확인하고 새 Job을 생성할 수 있습니다. OS 조회 또는 해제 검증에 실패하면 사용자 데이터 삭제 단계에 들어가지 않습니다. 앞에서 해제된 예약이 있을 수 있으며 자동 재등록하지 않습니다. 해제 도중 파일이나 최상위 삭제 대상이 추가·변경되면 `verify-data-plan` 단계에서 데이터 삭제를 중단합니다. 삭제 도중 새 자식 파일이 들어와도 재귀적으로 함께 삭제하지 않고 남깁니다. 이미 삭제된 개별 항목은 `deleted_entries`, 완전히 정리된 최상위 경로는 `deleted`, 남은 범위는 `remaining`에 표시합니다.

## Dashboard에서 초기화

기존 Dashboard의 **관리 · 초기화** 메뉴를 엽니다. Dashboard가 없다면 초기화만을 위해 새 서비스를 시작할 필요 없이 CLI를 사용해도 됩니다.

1. **OS 예약 진단**에서 고아 의심·확인 불가·조회 오류를 확인합니다. 다른 설치본의 예약도 표시될 수 있습니다.
2. **사용자 데이터 영구 초기화 → 삭제 대상 미리보기**를 누릅니다.
3. 대상 프로젝트 경로, 삭제 목록, OS 예약 수, 중단 이유를 확인합니다.
4. 계속하려면 `초기화`를 직접 입력하고 **사용자 데이터 영구 삭제…**를 누른 뒤 마지막 확인창에 동의합니다.
5. 결과를 확인합니다. 오류에는 실패 단계와 남은 데이터가 표시됩니다. 실패 후에는 새 미리보기가 필요합니다. 완료 시 **초기화된 Dashboard 다시 열기**로 빈 상태를 불러옵니다.

확인창에 동의하는 동안에는 기존 미리보기에 승인이 묶이고 다른 초기화·미리보기 요청을 막습니다. 연결이 끊기면 화면은 완료 여부가 불확실하다고 안내하며 자동으로 POST를 재전송하지 않습니다. 서버 작업은 연결이 끊겨도 계속되거나 완료될 수 있으므로 새 진단으로 상태를 확인하세요. 같은 승인 해시의 동시·이전 요청을 재사용해 새 Job까지 지우지 못하도록 서버 잠금과 현재 미리보기 검사를 수행합니다.

서버도 미리보기 해시와 Host·Origin·CSRF 검사를 수행합니다. 화면의 버튼 상태만으로 삭제 권한을 판단하지 않습니다. `uninstall`은 CLI에서 제공하며 Dashboard는 자기 프로그램 파일을 삭제하지 않습니다.

## 정상적인 완전 삭제

먼저 이 설치본에서 실행 중인 Job이 정상 완료될 때까지 기다립니다. 취소·강제 종료를 자동 수행하지 않습니다.

```sh
.venv/bin/python -m runner uninstall --help
.venv/bin/python -m runner uninstall
```

`reset`과 같은 데이터·예약 범위를 보여 주지만 `mode`는 `uninstall`입니다. 확인값은 목적별로 다르므로 `reset`의 확인값을 재사용할 수 없습니다. 제거 범위를 확인한 뒤 이 미리보기의 `plan_hash`로 승인합니다.

```sh
.venv/bin/python -m runner uninstall --confirm 확인값
```

`success: true`와 `next_steps`를 확인한 뒤 다음 순서로 마칩니다.

1. 이 명령이 끝날 때까지 기다립니다.
2. 이 설치본의 Dashboard를 실행했다면 해당 터미널에서 정상 종료합니다. 다른 설치본 서비스는 건드리지 않습니다.
3. 외부 보고서·백업·원격 배포 데이터의 별도 보존/제거 여부를 확인합니다.
4. 파일 탐색기에서 정확한 **프로젝트 폴더 하나**를 직접 삭제합니다. CLI는 실행 중 자신의 코드·가상환경을 지우지 않습니다. 데이터와 코드가 분리되어 있다면 경로를 각각 확인합니다.

폴더 삭제 명령을 복사해 실수하지 않도록 범용 `rm -rf`/재귀 삭제 명령은 제공하지 않습니다. 사용자가 선택한 폴더를 눈으로 확인하세요. 외부에 만들어 둔 바로가기·Skill 링크·별도 백업은 자동 제거하지 않습니다.

## 폴더를 먼저 삭제했다면: 재설치 후 예약 복구

폴더 삭제는 launchd·Task Scheduler·systemd 등록 해제를 뜻하지 않습니다. 예약은 남아 반복 실패할 수 있습니다. [설치 안내](../INSTALL.md)에 따라 **새 폴더**에 설치하고 같은 OS 사용자 계정에서 다음을 실행하세요. 원본 프로젝트가 없어도 OS 정의의 메타데이터를 읽습니다.

```sh
.venv/bin/python -m runner schedule-doctor
```

첫 일반 CLI 실행과 Dashboard 시작에서도 진단 결과를 안내합니다. 어떤 경우에도 시작 시 자동 삭제하지 않습니다. CLI 첫 진단 안내는 stderr로, 원래 명령 결과 JSON은 stdout으로 나옵니다. 진단 조회가 실패하면 다음 일반 CLI 실행에서 다시 안내합니다. 명시적인 `schedule-doctor`는 매번 새로 조회합니다.

| `status` | 화면 표시 | 의미와 처리 |
| --- | --- | --- |
| `healthy` | 정상 | 원본 실행 경로·필수 파일·예약 세대가 존재. 실행 성공까지 보장하는 상태는 아님. doctor 제거 금지 |
| `orphan` | 고아 의심 | 소유는 확인되지만 프로젝트·실행기·필수 파일 또는 예약 세대가 사라짐. 목록 검토 후 개별 승인 가능 |
| `unknown` | 확인 불가 | 소유·원본 경로·원본 정의/체크섬·OS 관찰을 확실히 확인하지 못함. 자동/일괄 제거 금지 |

삭제할 고아 예약 **한 개**의 `id`, `root`, `missing`, `reason`, `fingerprint`를 확인합니다. 반환된 `id`와 `fingerprint`로 아래 두 문자열을 바꾸세요. Windows의 `id`에는 선행 `\`가 포함됩니다.

```sh
.venv/bin/python -m runner schedule-doctor --remove "반환된 id" --confirm "반환된 fingerprint"
```

`removed`와 `verified: true`가 완료 증거입니다. 정상 예약, 확인 불가 예약, 실행 중인 예약 프로세스는 제거하지 않습니다. 원본 경로를 다시 연결하거나 다른 설치본에서 재적용해 상태가 달라졌다면 다시 진단해야 합니다. 진단 자체는 OS 예약과 프로젝트 사용자 데이터를 변경하지 않습니다. CLI 공통 초기화로 빈 데이터 루트의 `jobs/`, `runtime/` 및 승인 동기화 잠금 파일이 생길 수 있습니다.

같은 경로에 재설치한 경우 이전 세대의 예약도 진단합니다. 기존 데이터/예약이 모순되거나 소유권이 불확실하면 초기화 대신 수동 확인이 필요합니다. 다른 정상 설치본의 예약은 doctor에서 제거할 수 없습니다.

### 기존 예약과 새 식별 정보

macOS와 Windows의 기존 `local.scriptmanager.<경로해시>.<Job>[.<Schedule>]` 이름을 유지합니다. 설치별 무작위 ID와 데이터 루트·코드 루트·인터프리터·Job·Schedule·세대를 macOS plist/Windows Description에 추가합니다. macOS plist와 새 Windows XML에는 정의 체크섬도 들어갑니다. 현재 원본 상태 파일이 남아 있으면 실제 OS 정의의 체크섬과 설치 ID도 대조합니다. macOS는 실제 로드된 프로그램·인수·작업 폴더를 plist와 비교하며, Linux service의 실제 ExecStart와 timer의 연결 유닛도 확인합니다. 설치 ID는 경로에 묶여 있으며 데이터 폴더 복사본의 ID를 묵시적으로 재사용하지 않습니다.

이미 등록된 예약을 읽기만 해서는 바꾸지 않습니다. 원본 데이터가 있는 구버전 macOS/Windows 예약은 기존 상태 체크섬과 실제 실행 정의가 일치해야 소유를 인정합니다. 사용자가 기존 예약을 정상적으로 저장·적용하면 새 메타데이터가 붙습니다. 원본 체크섬이 사라졌거나 외부에서 수정된 구버전 예약은 확인 불가로 남기며 이름 접두사만 보고 지우지 않습니다. 이전 구현의 Windows 메타데이터 중 전체 XML 체크섬이 없는 작업은 원본 상태 체크섬이 있어야 합니다. 원본까지 사라졌다면 수동 확인 대상으로 남깁니다. Windows가 XML 내보내기에 필드·기본값을 추가하여 체크섬이 달라지는 경우도 보수적으로 확인 불가가 됩니다. 이 경우 원본 설치의 `schedule-remove`는 기존 로컬 체크섬을 이용할 수 있습니다. 실제 Windows별 XML 정규화 호환성은 아직 검증하지 않았습니다.

Linux 배포 유닛은 기존 `scriptmanager-<경로해시>-<Job>[-schedule-<Schedule>]` 이름을 유지합니다. 새로 승인한 배포부터 각 유닛의 `# ScriptManagerMetadata` 주석에 배포 설치 ID·원본 경로·실행 명령·체크섬을 넣습니다. 기존 immutable Package·release·OS 유닛은 변경하지 않습니다. 메타데이터가 없는 기존 systemd 유닛은 수동 확인 대상입니다.

## OS별 해제와 확인

일반적으로 위 CLI를 먼저 사용하세요. 아래는 CLI가 실패했을 때 읽기 전용 확인과 수동 복구를 위한 절차입니다. **이름 접두사만으로 삭제하거나 전체 예약을 일괄 삭제하지 마세요.** 소유권 불명확 예약은 자동 제거하지 않으며, 수동 조치도 원본 설치·백업·실행 명령으로 소유를 확정한 뒤 진행합니다.

### macOS: launchd

현재 로그인 사용자의 `~/Library/LaunchAgents/`와 `launchctl list`를 함께 조회합니다. 파일 없는 로드 예약도 목록에 포함하지만 원본을 검증할 수 없으면 확인 불가입니다. 다른 계정·시스템 LaunchDaemons는 자동 조사·변경하지 않습니다.

1. `schedule-doctor`가 알려 준 정확한 Label과 plist 경로를 기록합니다.
2. 터미널에서 `id -u`로 숫자 사용자 ID를 확인합니다. `launchctl print gui/숫자ID/정확한Label`로 `path`, `program/arguments`, `pid`를 확인합니다. plist는 `plutil -p "정확한 plist 경로"`로 확인합니다. 예약 메타데이터에는 비밀값을 저장하지 않습니다.
3. 고아로 확인되면 CLI의 `--remove … --confirm …`를 사용합니다. CLI는 실행 중인 `pid`가 있으면 중단합니다. Job 기록이 완료여도 예약을 실행한 CLI 프로세스가 아직 종료 중일 수 있습니다. 잠시 기다려 해당 프로세스가 자연 종료한 뒤 다시 확인하세요. 기존 `schedule-remove`와 재등록·실패 복구도 실행 중인 프로세스를 강제로 bootout하지 않습니다.
4. CLI를 사용할 수 없어 수동 해제가 필요하고 **소유가 확인된 비실행 예약**이라면 `launchctl bootout gui/숫자ID/정확한Label`을 실행합니다. `launchctl print`가 해당 서비스를 찾지 못하는지 확인한 **다음** 정확한 plist 한 개를 파일 탐색기에서 제거합니다.
5. plist가 없고 `launchctl print`도 서비스를 찾지 못해야 예약 해제 완료입니다. `launchctl` 권한/관찰 오류는 해제 완료가 아닙니다.

CLI는 launchctl의 서비스 없음 코드 113을 검증합니다. `bootout` 실패·관찰 실패 시 plist와 사용자 데이터를 보존합니다. 로그인 세션이 없는 환경에서는 GUI 도메인 조회가 실패할 수 있습니다. 해당 계정으로 로그인한 뒤 다시 확인하세요. 기존 관련 없는 서비스는 재시작하거나 종료하지 않습니다.

### Windows: Task Scheduler

현재 사용자 권한으로 조회 가능한 작업 중 Script Manager 형식을 확인합니다. 관리자 권한 상승이나 다른 계정 작업 제거는 자동 수행하지 않습니다.

1. `schedule-doctor` 또는 **작업 스케줄러 → 작업 스케줄러 라이브러리**에서 정확한 작업 이름을 찾습니다.
2. **설명**, **동작**의 프로그램·인수·시작 위치, 실행 계정과 상태를 확인합니다. 명령으로는 `schtasks /Query /TN "정확한 작업 이름" /XML`을 사용합니다.
3. CLI는 Windows PowerShell의 숫자 작업 상태로 실행 중인지 확인하고, 소유가 확인된 고아만 `schtasks /Delete`로 제거합니다. Windows PowerShell 또는 OS 조회를 사용할 수 없으면 보존하고 중단합니다.
4. 수동 제거가 필요하면 소유권이 확정되고 실행 중이 아닌 해당 작업 하나만 작업 스케줄러에서 삭제합니다. 작업을 강제 종료하지 않습니다.
5. 목록을 새로고침하고 `schtasks /Query /TN "정확한 작업 이름" /XML`에서 사라졌는지 확인합니다. 개별 조회 실패만으로 삭제 성공으로 판단하지 말고 `schtasks /Query /FO CSV /NH` 목록도 정상 조회되어 해당 이름이 없는지 확인합니다.

정상적인 기존 프로젝트에서는 `schedule-remove JOB --schedule SID`와 원본 상태 체크섬을 이용할 수도 있습니다. 원본 데이터가 사라진 구버전 작업은 doctor에서 자동 제거하지 않습니다.

### Linux: 기존 SSH 배포의 systemd user

Linux 로컬 Job 예약 등록은 여전히 미지원입니다. doctor는 **현재 Linux 호스트·현재 사용자**의 systemd user 예약을 조사하며, 로컬 컴퓨터에서 원격 서버로 SSH 접속하지 않습니다. 원격 서버에서는 그 서버에 로그인하고 관리 도구를 설치한 뒤 진단하세요. SSH 작업은 별도 승인이 필요합니다.

1. `systemctl --user list-timers --all`과 `systemctl --user list-unit-files 'scriptmanager-*'`로 목록을 확인합니다. 사용자 systemd 세션에 접근할 수 없으면 오류를 해결하기 전 삭제하지 않습니다.
2. 정확한 유닛에 `systemctl --user cat 정확한유닛`과 `systemctl --user show 정확한유닛`을 사용해 원본 경로·메타데이터·ExecStart·상태·drop-in을 확인합니다.
3. doctor는 `~/.config/systemd/user/`의 메타데이터·실행 경로·전체 정의 체크섬과 OS의 로드 원본을 검증합니다. 외부 drop-in, 다시 로드되지 않은 변경, 메타데이터 없는 기존 유닛은 확인 불가로 보존합니다.
4. 고아 timer를 먼저 개별 승인해 제거한 뒤, 연결된 비실행 service도 목록에서 개별 승인합니다. timer 해제는 Job 서비스를 강제 종료하지 않습니다. doctor는 활성 service를 제거하지 않습니다.
5. 수동 복구라면 소유가 확정된 timer 하나에 `systemctl --user stop 정확한.timer`, `systemctl --user disable 정확한.timer`를 실행하고 비활성/비활성화 상태를 확인합니다. 정확한 timer 파일과 **실행 중이지 않은** 해당 service 파일만 제거하고 `systemctl --user daemon-reload`합니다.
6. `systemctl --user show 정확한유닛`에서 `LoadState=not-found`이고 비실행 상태인지, 해당 유닛 파일이 없는지 확인합니다. 다른 프로그램의 유닛은 그대로 둡니다.

기존 remote helper가 만든 메타데이터 없는 유닛은 원격 deployment의 `activation.json`, release `manifest.json`과 OS 파일·실행 경로를 사람이 대조해야 합니다. 판별할 근거가 없으면 제거하지 않습니다. 로컬 `reset`/`uninstall`이 원격 배포까지 정리한다고 가정하지 마세요. 배포 루트 자체를 `--root`로 지정해 로컬 데이터 초기화와 혼용하는 것도 지원하지 않습니다.

## 실패 시 복구

| 상황 | 데이터 상태와 다음 행동 |
| --- | --- |
| 실행·잠금·대기 기록 또는 예약 적용 중/복구 실패 기록이 존재 | 초기화 중단. 정상 종료를 기다리고 같은 Run·OS 예약을 조회. 자동 취소 없음 |
| 미확정 배포 이력(`pending`, `unconfirmed`)이 존재 | 원격 상태를 추정하지 않고 이력을 보존. 원격 검증은 별도 승인 작업이며 로컬 초기화가 접속하지 않음. 기존 verify는 이력을 자동 재확정하지 않으므로 운영자가 증거·백업을 보존한 별도 복구를 판단해야 함 |
| 중첩 설치본·Git 프로젝트·링크·마운트가 존재 | 다른 데이터 경계를 보존하고 중단. 별도 보관 위치로 안전하게 분리하거나 OS 담당자가 마운트를 확인한 뒤 새 미리보기 검토. 식별 파일만 지워서 검사를 우회하지 않음 |
| OS 목록/정의/상태 조회 실패 | 데이터 삭제 중단. OS 권한·로그인 세션·도구 접근을 해결한 후 재진단 |
| 소유권 불명확·외부 수정·체크섬 없음 | 보존. 백업/원본 설치와 OS 실행 명령을 대조. doctor 강제 삭제 옵션 없음 |
| OS 해제 실패 또는 성공을 검증할 수 없음 | 사용자 데이터 보존. 일부 예약이 이미 해제되었을 수 있으므로 `removed_schedules`와 OS 실제 상태를 확인하고 새 미리보기 생성 |
| `delete-data`/`verify-data` 단계 실패 | 일부 데이터는 이미 삭제되었을 수 있음. `deleted_entries`, `deleted`, `remaining`, `phase`, `error` 확인. 파일 권한·디스크 상태를 해결하고 새 미리보기부터 진행 |
| 브라우저 응답/연결을 잃음 | 자동 재전송 금지. `list`, `schedule-doctor`와 새 미리보기로 실제 상태를 확인. 결과 화면만으로 성공을 추정하지 않음 |
| 이전 프로젝트 경로가 이동됨 | OS 정의는 자동 추적하지 않음. 이전 설치 예약과 새 설치 예약을 대조하고 각각 승인해 정리·재등록 |
| 설치 ID가 복사되거나 손상됨 | `installation.json`을 지우고 무시하지 말고 원본/복사 경로와 OS 예약을 먼저 확인. 임의 ID 교체로 기존 예약을 인수하지 않음 |

초기화는 안전한 단계별 작업이며 데이터 삭제 전체를 되돌리는 트랜잭션은 아닙니다. 다른 프로그램/터미널에서 파일·예약을 동시에 수동 수정하지 마세요. 같은 구현의 관리 명령 간 충돌은 프로젝트 잠금으로 차단하지만 OS에는 정의 비교와 제거를 하나의 원자적 명령으로 처리하는 기능이 없습니다. 외부 OS 관리자·이전 버전 프로세스와의 동시 변경을 완전히 배제하지 못합니다. POSIX 삭제는 디렉터리 descriptor와 O_NOFOLLOW, 각 항목의 inode·장치·파일 상태를 확인합니다. Windows 경로 기반 삭제와 reparse 검사는 실환경 미검증이며 외부의 악의적 동시 교체에 대한 완전한 원자성을 주장하지 않습니다. 초기화 중에는 다른 터미널·OS 관리 도구에서 파일·예약을 변경하지 마세요. 저장장치의 안전 소거, 백업·휴지통·클라우드 사본 삭제를 보장하지 않습니다.

실제 플랫폼 검증 범위와 실행한 테스트는 [검증 기록](validation.md)에 별도로 적습니다. Windows/Linux 모의 테스트 통과가 해당 OS 실검증을 뜻하지는 않습니다.
