# Script Manager v0.1.1 — Stability & Usability Update

Product version: `0.1.1`. For stable updates, select the published Tag from [official Releases](https://github.com/nstgmg/script-manager-oss/releases/latest) and verify its commit and VERSION.

Windows validation documentation corrected on 2026-11-18 (Asia/Seoul). The existing `v0.1.1` tag and distributed product code are unchanged; [current validation records](https://github.com/nstgmg/script-manager-oss/blob/main/docs/validation.md#windows-verification-correction--2026-11-18) contain the correction.

## Overview

This update adds explicit installation maintenance and schedule recovery tools, improves Dashboard notifications, and changes Windows filesystem handling to better preserve metadata and approved data boundaries. Script Manager remains a local, single-user tool that executes trusted scripts with the user's OS permissions.

## Highlights

- Inspect OS reservations with `schedule-doctor` and remove an individually confirmed, verifiably owned orphan.
- Preview installation data cleanup with `reset` or `uninstall`; execution requires the current confirmation hash.
- Review schedule diagnosis and reset previews in the Dashboard's management view.
- Get consistent notification dismissal, five-second automatic closing, and reduced-motion behavior.

## Added

- `schedule-doctor`: read-only OS reservation inventory for current-user macOS launchd, Windows Task Scheduler, and Linux deployment systemd user units. Healthy and unknown reservations are preserved by the orphan-removal command.
- `reset` and `uninstall`: preview-first maintenance with ownership checks, active-work blockers, verified OS removal before data deletion, and partial-progress reporting. `uninstall` leaves the program folder in place and provides manual removal instructions.
- Dashboard schedule diagnosis and reset preview/confirmation, including `GET /api/schedule-doctor`, `GET /api/reset`, and CSRF-protected `POST /api/reset`.
- A standard-library bootstrap helper: `python scripts/bootstrap.py` inspects the local environment; `--prepare` is limited to eligible new or partial environments without operating data.

## Improved

- Installation identity and definition metadata support reservation ownership checks. Newly applied local schedules and future Linux deployments carry this information; existing reservations and immutable Packages are not rewritten by diagnosis or a code update.
- Maintenance coordinates with Job operations, report generation, and automatic retention cleanup. It checks approved inventory again after schedule removal and deletes only approved entries.
- Dashboard notifications use independent lifetimes, accessible close buttons, keyboard interaction, and a 180 ms fade after five seconds. Error notifications remain until dismissed; reduced-motion preferences suppress the fade.
- Windows installation guidance now describes PowerShell failure handling, resuming the same checkout, and manual ACL diagnosis without automatic permission resets.

## Fixed

- `run-dashboard` now reports an exhausted observation deadline as `wait_timed_out` when the final status request times out at that deadline, preserving the accepted Run ID for observation without resubmission.
- Saved-result file filters reject rooted, drive-relative, UNC, and traversal forms consistently across platforms.
- Windows task ownership checks can use the original installation's exact recorded post-registration XML when Windows normalizes the generated definition. Changed definitions or missing evidence remain protected.
- Windows data-directory creation uses parent ACL inheritance. Existing ACLs are not modified or repaired automatically.
- Windows metadata publication uses delete-sharing readers and native atomic replacement. Saved-result metadata reads, source snapshots, and approved maintenance deletion use a dedicated handle-based NTFS backend; approval records retain native file identity and timestamp fields.
- Windows lock acquisition no longer writes an initialization byte through an existing hardlink.

These Windows implementation changes are covered by the historical integrated Windows completion report described below, with reusable results for the unchanged core backend and separate follow-up smoke records.

## Compatibility Changes and Updating

- **Windows filesystem restriction:** the new confined I/O backend requires local fixed NTFS drive paths. UNC/network paths, removable drives, FAT/exFAT, and other filesystems are rejected on affected snapshot, saved-Run-metadata, and maintenance paths. Atomic publication also requires support for `FileRenameInfoEx` POSIX replacement semantics; unsupported operations return errors without an unsafe fallback. Existing verification and follow-up smoke records support updates on Windows 10/11 installations meeting the path, filesystem, API, permission and data-preservation conditions. Ordinary local NTFS use is not itself a reason to defer. Review [installation requirements](https://github.com/nstgmg/script-manager-oss/blob/main/INSTALL.md#windows-파일시스템과-원자-저장-요구-사항) and [existing Windows update checks](https://github.com/nstgmg/script-manager-oss/blob/main/UPDATE.md#windows-기존-설치의-v011-업데이트-전-확인). Unsupported or unresolved installation-specific compatibility remains a reason to defer; do not automatically relocate data, change ACLs, or re-register schedules.
- No Job YAML schema, public parameter contract, or declared runtime dependency change was identified. No bulk data migration or automatic schedule re-registration is introduced.
- The first use of ownership-aware operations may create installation identity metadata. Keep the same data root; copied or moved identity records require manual review rather than automatic adoption.
- Existing Windows ACL problems require separately reviewed recovery. Updating code does not repair inaccessible data. Previous maintenance confirmations must be regenerated, including the Windows approval schema change.
- Follow [UPDATE.md](https://github.com/nstgmg/script-manager-oss/blob/main/UPDATE.md), preserving Jobs, schedules, Output, State, Workspace, secrets, Packages, and deployment history. An update does not require running `reset` or `uninstall`.

## Known Limitations

- **Maintenance is destructive:** confirmed reset/uninstall permanently deletes managed user data, including Job source, logs, Output/State/Workspace, trash, Packages/history, and the root `.env`. It is not an undoable trash operation or an all-or-nothing transaction. Partial failures require a fresh preview and review of reported progress.
- **Windows:** verification applies to the recorded integrated and subsequent smoke scopes, not every Windows/Python/token/driver combination or every Dashboard operation. Fixture-based scheduler ownership checks remain distinct from actual OS registration/trigger/removal evidence. T1/T2 fixture results and T3/T4 report checks do not certify later notification UI changes. The corrected clipboard assertion does not establish a Windows automated rerun or actual OS clipboard paste.
- **macOS:** calendar date arrival, sleep/wake, login/reboot persistence, Intel Macs, and other OS/Python combinations remain outside the recorded validation scope.
- **Linux:** local Job scheduling is unsupported. Current-user deployment-unit diagnosis is implemented, but native Linux/systemd and real SSH deployment remain unverified. Remote `required_env`, local-style managed data paths, reports, and result/log synchronization retain their documented limitations.
- Ownership checks preserve unknown and externally changed reservations. Native tools do not provide an atomic compare-and-remove operation against concurrent external OS edits. This tool is not a hostile-user sandbox or a secure-erasure utility.
- Other unresolved code-scanning findings and platform/security follow-ups remain after the individual #169/#170 False positive dismissals. The earlier audit's unauthenticated alert-inventory request failed; the later signed-in observations above are separate evidence. Successful CodeQL execution does not prove those other findings resolved or certify security.
